# План технических работ: мультиплатформенный агент поиска вакансий

Дата: 2 ноября 2026 года.

Статус: **черновик на обсуждение**. Архитектура (ядро + адаптеры) согласована с пользователем, автоотклик исключён из объёма. Список платформ и формат доставки в Telegram пока не зафиксированы — этапы 6 и 7 содержат заглушки и критерии приёмки, которые заполняются после их выбора.

> **Обновлено 03.11.2026:** план прошёл две независимые рецензии, замечания и решения пользователя сведены в отревьюенную редакцию v2 — [12-multiplatform-plan.md](../knowledge-base/12-multiplatform-plan.md) в базе знаний. Работу вести по ней; этот черновик остаётся как исходник.

**Цель:** один локальный агент, который собирает вакансии с нескольких площадок, убирает дубли между ними, фильтрует по согласованным правилам, готовит для каждой подходящей вакансии сопроводительное письмо и советы по правке резюме, и присылает всё это в Telegram. Пользователь откликается сам.

**Архитектура:** один асинхронный Python-процесс. Общее ядро (нормализация → дедупликация → правила → LLM → доставка) + подключаемые адаптеры платформ (поиск и чтение). SQLite как единственное хранилище состояния. Telegram-бот для доставки и команд.

**Техстек:** Python 3.9+, httpx, sqlite3 (WAL), python-dotenv, unittest. Playwright уходит из зависимостей, если ни одна выбранная платформа не потребует браузера для чтения.

**Предыдущие документы:** [дизайн hh-агента](../superpowers/specs/2026-10-19-job-agent-design.md), [план реализации hh-агента](../superpowers/plans/2026-10-21-job-agent.md), [база знаний](../knowledge-base/README.md).

## 1. Рамки и принципы

### 1.1. Что строим

- Сбор вакансий с нескольких платформ через адаптеры с единым интерфейсом.
- Единая каноническая модель вакансии; вся платформенная специфика заперта в адаптере.
- Дедупликация между платформами: точный ключ + эмбеддинги (с fallback без внешнего сервиса).
- Детерминированные правила отбора (Python, удалёнка, зарплата, грейд) — общие для всех платформ.
- LLM-скоринг соответствия резюме и генерация письма + советов по правке резюме под конкретную вакансию.
- Доставка в Telegram: ссылка (все площадки-источники), оценка, письмо, советы.
- Управление по командам бота (`/status`, `/history`, `/letter`, `/skip` и т.д.).

### 1.2. Что явно исключаем

- **Автоотклик целиком.** Удаляются: браузерная отправка, режим `HH_LIVE`, привязка `resume_id`, сверка неопределённых откликов, таблица `attempts`, статусы `sending`/`sent`/`unknown`, капча при отправке, `send_interval`.
- Обход капчи, скрытые методы сайтов, экспорт чужих сессий (правило сохраняется).
- Деплой на сервер: агент остаётся локальным, запуск/остановка на компьютере.
- Выдумывание фактов: письма и советы по резюме строятся только на фактах из согласованного профиля.

### 1.3. Переносимые из текущего проекта принципы

- Владелец-онли Telegram: бот отвечает только одному ID в личном чате.
- Всё состояние в SQLite, идемпотентный перезапуск с места прерывания; outbox переживает рестарты и сбои Telegram.
- Ошибка одной платформы не останавливает остальные; требующие внимания состояния (`AttentionRequired`) паузуют только затронутую платформу.
- Секреты только в `.env` и `.state/`, в Git не попадают.
- Экономия LLM-вызовов: модель вызывается только для вакансий, прошедших дешёвые фильтры.

## 2. Целевая архитектура

### 2.1. Конвейер

```
 адаптеры (параллельно, каждый по своему расписанию)
   search → список новых (native_id, url, published_at, заголовок)
        │
   отсев уже известных по базе
        │
   fetch → полное описание → каноническая Vacancy
        │
   дедупликация: точный ключ → эмбеддинги (порог 0.93)
        │
   жёсткие правила (детерминированно, без LLM)
        │
   LLM-скоринг соответствия профилю (дешёвая модель)
        │
   LLM-генерация: письмо + советы по резюме (строгий JSON)
        │
   outbox → Telegram (сообщение с ссылками, оценкой, письмом, советами)
```

### 2.2. Структура пакета

```
job_finder/
  __main__.py            # CLI: init, configure, pair, doctor, run
  config.py              # платформы, критерии, интервалы, LLM, Telegram
  models.py              # канонические модели: Vacancy, Salary, Decision, Letter, ResumeAdvice
  store.py               # SQLite: jobs, clusters, settings, inbox, outbox, skip_events
  rules.py               # детерминированные правила отбора (не зависят от платформы)
  dedupe.py              # точный ключ + эмбеддинги, кластеры
  scoring.py             # LLM-скоринг соответствия
  writer.py              # LLM-генерация письма и советов по резюме
  llm.py                 # общий LLM-клиент: JSON-режим, повторы, кэш, учёт стоимости
  engine.py              # оркестратор: цикл конвейера и планировщик
  telegram.py            # бот: отправка outbox + обработка команд
  adapters/
    __init__.py          # реестр адаптеров, протокол SourceAdapter
    base.py              # общие хелперы: HTTP, rate limiter, backoff, парсинг
    hh.py                # hh.ru (миграция из текущего hh.py, бывш. hhapi.py / browser — только чтение)
    # habr.py, remoteok.py, ... — этап 6
```

### 2.3. Каноническая модель вакансии

```python
@dataclass(frozen=True)
class Vacancy:
    source: str              # "hh", "habr", "remoteok", ...
    native_id: str           # ID внутри платформы
    url: str                 # прямая ссылка
    title: str
    company: str             # очищенное название
    description: str
    requirements: str        # часть описания, относящаяся к требованиям
    salary: Salary | None    # minimum, maximum, currency, period, raw
    remote: bool | None      # None = не подтверждено
    published_at: str | None
    closed: bool = False
    language: str = "ru"     # язык описания: для языка письма
    raw: dict                # необработанные данные платформы (отладка, репарсинг)
```

Ключ записи в базе — `source:native_id`. Ссылка `url` строится адаптером; ядро не умеет собирать URL платформ.

### 2.4. Схема базы (целевая)

- `jobs` — ключ `id = source:native_id`; добавляются колонки `source`, `published_at`; колонки `resume_id` и `evidence` удаляются.
- `clusters(id, rep_job_id, centroid BLOB, created)` — кластер дублей.
- `job_embeddings(job_id, embedding BLOB)` — вектор для каждого прочитанного; используется и для дедупа.
- `settings`, `inbox`, `outbox`, `skip_events` — без изменений.
- `attempts` — удаляется.
- Статусы вакансий: `found` (известна, не прочитана), `read` (описание получено), `rejected` (правила или скоринг, с причиной), `needs_clarification` (неоднозначно), `ready` (письмо готово, ждёт доставки), `delivered` (отправлено в Telegram), `closed` (вакансия закрыта), `error` (сбой обработки).

### 2.5. Протокол адаптера

```python
class SourceAdapter(Protocol):
    name: str
    def __init__(self, config): ...
    async def search(self, criteria, since) -> list[RawHit]
    async def fetch(self, key) -> Vacancy
```

`search` возвращает только дешёвые поля листинга; `fetch` достаёт полное описание и отдаёт каноническую `Vacancy`. Вся пагинация, аутентификация, лимиты и парсинг — внутри адаптера. Исключения наружу: `AttentionRequired` (нужен человек: вход, капча), `RateLimited` (повторить позже), `VacancyUnavailable` (закрыта/удалена).

### Этап 2. Протокол адаптера и реестр

**Цель:** оформить контракт адаптера и механику подключения, чтобы новые платформы добавлялись файлом + строкой в конфиге.

**Файлы:** `adapters/__init__.py`, `adapters/base.py`, `config.py`, `engine.py`.

- [ ] Реестр адаптеров: имя → класс; `PLATFORMS=hh,...` в `.env` включает подмножество.
- [ ] `adapters/base.py`: общий HTTP-клиент (httpx), rate limiter на платформу, экспоненциальный backoff на 429/5xx, таймауты, повтор при `RateLimited` без потери состояния.
- [ ] Планировщик: у каждой платформы свои `last_search` и интервал поиска; платформы работают параллельно, сбой одной изолирован (`AttentionRequired` паузует только её).
- [ ] Документация контракта в `docs/` (короткий ADR: что обязан гарантировать адаптер).
- [ ] Тесты реестра и планировщика на фейковом адаптере (без сети).

**Критерий выхода:** добавление нового адаптера не требует правок ядра; фейковый адаптер в тестах проходит конвейер целиком.

### Этап 3. Дедупликация

**Цель:** один кластер на одну вакансию независимо от числа площадок.

**Файлы:** `dedupe.py`, `store.py` (кластеры и эмбеддинги), `tests/test_dedupe.py`.

- [ ] Нормализация названия и компании: регистр, пунктуация, «Senior»/«Сеньор», лишние пробелы, юридические формы (ООО, Inc).
- [ ] Точный ключ `(norm_company, norm_title)` → проверка существующего кластера.
- [ ] Кандидаты для близкого сравнения: записи с той же нормализованной компанией **или** тем же нормализованным названием (уже отфильтровано — дёшево).
- [ ] Эмбеддинги: предпочтительно endpoint `/embeddings` провайдера LLM (конфигурируется); fallback — локальный SimHash по описанию, если провайдер эмбеддинги не даёт.
- [ ] Порог косинусной близости ~0.93 (вынести в конфиг); сравнение «название + компания + первые ~800 символов описания», чтобы различать две реально разные вакансии с одинаковым названием в одной компании.
- [ ] При совпадении: новая запись не создаётся, к кластеру добавляется `source:native_id` и ссылка; запись кластера обновляется (например, появилась зарплата на другой площадке).
- [ ] Тесты: точные дубли, переформулировки, ложные срабатывания (одинаковые названия, разные описания), граница порога.

**Критерий выхода:** тесты на граничных случаях зелёные; на живых данных hh + минимум одной площадки дубли схлопываются (проверка на этапе 6/8).

### Этап 4. Writer v2: скоринг, письмо, советы по резюме

**Цель:** один проход LLM даёт оценку соответствия, письмо и конкретные правки резюме под вакансию.

**Файлы:** `scoring.py`, `writer.py`, `llm.py`, `profile/facts.json` (согласованный профиль фактов), `tests/test_writer.py`.

- [ ] Профиль фактов: вынести согласованные факты резюме в отдельный файл (иммутабельный для модели), не зависящий от резюме на hh.
- [ ] `scoring.py`: дешёвая модель, JSON-ответ `{score: 0..100, verdict: apply|skip, reason}`; кэш по `(job_id, версия профиля)`.
- [ ] `writer.py`: JSON-схема ответа:
  ```json
  {
    "letter": "текст письма на языке вакансии",
    "resume_advice": [
      {"section": "skills|experience|summary|...", "action": "add|emphasize|reorder|remove|highlight", "detail": "..."}
    ],
    "prep_topics": ["2–3 темы для подготовки"]
  }
  ```
- [ ] Безопасность контента: факты только из профиля; запрет выдуманных достижений; ограниченные утверждения помечаются, как в текущей версии; защита от prompt-injection в тексте вакансии (вакансия — данные, не инструкции).
- [ ] `llm.py`: общий клиент Chat Completions + JSON-режим, валидация ответа схемой, повтор при невалидном JSON, учёт токенов и стоимости в журнале.
- [ ] Тесты: невалидный JSON, галлюцинированный факт, язык письма, пустые советы, injection-текст в описании.

**Критерий выхода:** для каждой прошедшей правила вакансии есть оценка с причиной, письмо и ≥1 конкретный совет по резюме; стоимость вызова фиксируется в логе.

### Этап 5. Telegram: формат доставки и команды

**Цель:** удобное сообщение-«карточка» на одну уникальную вакансию + команды управления.

**Файлы:** `telegram.py`, `engine.py` (формирование текста), `tests/test_telegram.py`.

- [ ] Шаблон сообщения: название, компания, зарплата, формат, **все ссылки кластера**, оценка + причина, письмо, советы по резюме, темы подготовки.
- [ ] Режимы доставки (по открытому вопросу №2): немедленная отправка каждой подходящей ИЛИ сводка топ-N за цикл; в обоих случаях `/letter <id>` и `/history` показывают детали.
- [ ] Команды: `/status` (состояния платформ и очереди), `/history`, `/letter source:native_id`, `/skip source:native_id` (занести в отсев, чтобы не предлагать повторно), `/help`.
- [ ] Outbox как единственный путь наружу; повторы при сбое Telegram; лимит длины сообщения (разбивка/сокращение).
- [ ] Тесты: лимиты длины, недоступный Telegram, неавторизованный пользователь, дубли обновлений.

**Критерий выхода:** сообщения доходят по шаблону, команды работают, очередь переживает рестарт.

## 4. Миграция данных

- `PRAGMA user_version` повышается; миграция создаёт новую схему и переносит данные из старой (id → `hh:native_id` для существующих записей hh, письма и причины сохраняются).
- Удаляются: `attempts`, колонки `resume_id`/`evidence`, статусы откликов; записи в них переводятся в `delivered`/`rejected` по текущему смыслу.
- `settings`: ключи `HH_LIVE`, `next_send_at` и т.п. вычищаются; добавляются новые с умолчаниями.
- Миграция идемпотентна и выполняется при первом запуске; до миграции — резервная копия `.state/agent.sqlite3` (этап 0).

## 5. Тестирование

- Модульные тесты: правила, дедуп, writer, store, планировщик — без сети и без LLM (замоканные ответы).
- Адаптеры тестируются на записанных HTTP-фикстурах; живые запросы — только при ручной проверке.
- Сквозной тест конвейера на фейковом адаптере: от `search` до записи в outbox.
- Инварианты, проверяемые всегда: идемпотентный перезапуск, один outbox-канал, отсутствие дублей в базе, стоимость/токены в логе.

## 6. Риски и ограничения

| Риск | Мера |
| --- | --- |
| Бан/лимиты платформы | адаптеры с rate limiter, уважение лимитов, пауза платформы при 429/капче |
| Ложное объединение дублей | порог 0.93 + учёт описания + ручная проверка кластеров на приёмке |
| Нет endpoint эмбеддингов у провайдера | fallback SimHash; качество дедупа чуть ниже, фиксируется в отчёте |
| Стоимость LLM | скоринг на дешёвой модели, кэш, вызовы только после фильтров |
| Prompt-injection в тексте вакансии | вакансия передаётся как данные, вывод валидируется схемой |
| LinkedIn без API | либо ручной экспорт, либо отказ от платформы — решить на этапе выбора |
| Python 3.9 | без зависимостей, требующих новее; эмбеддинги локально не обучаем (только API/SimHash) |
