## 0. Методология и исходные данные

Это план **переделки существующего проекта**, а не новый проект. Поэтому источником истины в этой рецензии является **фактический код рабочего дерева и живая база**, а не `docs/knowledge-base/` (пользователь предупредил, что КБ может быть неактуальна). КБ использовалась только как ориентир; все утверждения ниже привязаны к строкам кода.

Фактическое состояние, проверенное в момент рецензии:

| Факт | Значение |
| --- | --- |
| Тесты | 156/156 зелёные (пересчитано пофайлово: browser 27, cli 11, config 5, engine 29, hh 22, letters 9, rules 9, store 19, telegram 25) |
| Рабочее дерево Git | ветка `codex/job-finder`, **17 файлов изменено (+1140/−247), НЕ закоммичено**; `job_finder/hh.py`, `tests/test_hh.py`, `scripts/setup.command`, `docs/*` — **untracked**. Последний коммит `66cacfe` не содержит перехода на программный API HH |
| База `.state/agent.sqlite3` | `user_version=3`, живые данные: `found` 1573, `needs_clarification` 72, `ready` 31, `sent` 2, `rejected` 2, `closed` 2, `error` 8 |

Главный факт, который план упускает: **переход на программный API HH (вся ветка работы 30.10) ещё не закоммичен**. Этап 0 обязан начинаться с коммита текущего состояния, иначе ветка `feature/multiplatform` отпочкуется от грязного дерева и переделка может потерять именно ту версию, которую план берёт за основу.

## 1. Вердикт

Архитектурное направление правильное, преемственность с проверенными решениями проекта соблюдена, объём вырезан разумно (автоотклик целиком). План готов к обсуждению, но **начинать работу по нему в текущем виде нельзя** — есть критические недоделки:

**P0 — блокирует старт этапов 1/3/4:**
1. Этап 1 недооценивает объём: удаление автоотклика ломает/удаляет **не менее ~60 из 156 тестов** и три подсистемы (`claim/finish/recover`, `attempts`, глобальная пауза). Это самый большой кусок всего плана, описанный одним чекбоксом.
2. Схема БД (п. 2.4) **не содержит** нормализованных колонок для дедупликации (`norm_company`/`norm_title`) и таблицы ссылок кластера на источники — без них этапы 3 и 5 нереализуемы как написаны.
3. Writer v2 молча отменяет самое сильное свойство безопасности текущей системы — дословную сверку письма с локальной сборкой ([job_finder/letters.py:106](../../job_finder/letters.py#L106)); замена не предложена. JSON-валидация не обосновывает факты.
4. Внутреннее противоречие: «один проход LLM» (цель этапа 4) против двухшагового конвейера `scoring.py + writer.py` (п. 2.1).
5. Синтаксис канонической модели `Salary | None` требует Python 3.10+, при заявленном стеке Python 3.9+.

**P1 — требует решения до соответствующих этапов:**
6. Параллелизм адаптеров против синхронного SQLite в asyncio-цикле (п. 2 этапа 2) — не решено, а это главное скрытое архитектурное решение всего плана.
7. Порог 0.93 косинуса не переносится на SimHash-fallback (разные метрики) — нужно два порога.
8. Версионирование эмбеддингов (смена провайдера/модели → все векторы несравнимы) — не упомянуто.
9. `DELIVER=false` используется в этапе 8, но флага нет ни в конфиге, ни в этапе 5.
10. LLM-скоринг с вердиктом `apply|skip` потенциально противоречит одобренной философии широкого охвата (дизайн 19.10: несоответствие навыкам не блокирует).
11. Конфликт принципа 1.2 («скрытые методы сайтов исключаем») с сохранением `hh.py` — эмуляции официального Android-приложения ([job_finder/hh.py:39](../../job_finder/hh.py#L39)). Нужно явно подтвердить решение от 30.10 как согласованное исключение, иначе план противоречит сам себе.

Детали — в разделах ниже.

## 2. Что план делает правильно

- **Декомпозиция «ядро + адаптеры»** — правильная: каноническая `Vacancy`, вся платформенная специфика заперта в адаптере, ядро не собирает URL платформ. Текущий код уже почти так устроен (`rules.py` работает на модели, а не на hh).
- **Честный статус черновика** с критериями приёмки на каждом этапе и открытыми вопросами — сильная сторона документа.
- **Экономика LLM**: вызовы только после дешёвых фильтров, дешёвая модель для скоринга, кэш, учёт стоимости. Соответствует принципу текущего проекта.
- **Идемпотентность и outbox**: перезапуск с места прерывания, outbox переживает сбои Telegram — это проверенные паттерны текущего кода, корректно перенесены.
- **Дедупликация с fallback**: точный ключ → эмбеддинги → SimHash, порог в конфиге, ручная проверка 20–30 кластеров на приёмке. Правильный скелет.
- **Миграция**: бэкап до миграции (этап 0), идемпотентность, `PRAGMA user_version`, перенос писем и причин, обработка пилотной записи `137924141` (сейчас она захардкожена в [job_finder/store.py:52](../../job_finder/store.py#L52)).
- **Риск-таблица** — полезна, но неполна (см. раздел 7).
- **Исключения** (автоотклик, капча, сервер, выдумывание фактов) — правильные и сокращают объём.
- Правильная последовательность: правила → скоринг → письмо (дешёвое отсеивает раньше дорогого).

## 3. Базовое состояние (что план должен был явно зафиксировать)

- Текущий конвейер одноплатформенный: `search → prepare(→ready) → send(apply) → reconcile` ([job_finder/engine.py](../../job_finder/engine.py)). Дедупа и скоринга нет.
- `rules.evaluate()` уже работает на канонической модели, но **порог 150 000 захардкожен** в [job_finder/rules.py:59-64](../../job_finder/rules.py#L59) — план правильно требует выноса в конфиг.
- `hh.py` уже содержит ~80% будущего `adapters/base.py`: rate limiter (`min_interval=0.4`), автообновление токена, санитизация ошибок, пагинация с разбиением по 4 диапазонам опыта, капча → `AttentionRequired` ([job_finder/hh.py:224-295](../../job_finder/hh.py#L224)). **План нигде не говорит, что `base.py` — это извлечение из `hh.py`, а не новый код**; этап 2 нужно переформулировать как рефакторинг-извлечение.
- URL hh захардкожен в двух местах: `Vacancy.url` ([job_finder/models.py:27](../../job_finder/models.py#L27)) и дневная сводка ([job_finder/engine.py:156](../../job_finder/engine.py#L156)). План упоминает первый, но не второй — при рефакторинге его легко пропустить.
- Валидация `HH_RESUME_ID` ([job_finder/config.py:60](../../job_finder/config.py#L60)) и весь `send_interval`/`HH_LIVE` удаляются — правильно, но вместе с ними уходит и глобальная пауза (см. этап 1).
- В живой БД 31 запись `ready` со старыми письмами — миграция должна явно решить их судьбу (план молчит).

## 4. Разбор по этапам

### Этап 0. Базовая линия

**Хорошо**: зелёный прогон (подтверждён рецензией), бэкап БД, поведенческий чек-лист.

**Пробелы:**
- **Нет пункта «закоммитить текущее состояние»**. Дерево грязное: 17 файлов (+1140/−247), `hh.py` untracked. Создание ветки `feature/multiplatform` из этого дерева рискованно: переименование пакета в этапе 1 затрёт историю «до/после», а запасная копия только БД (не кода) ничего не спасёт, если рефакторинг пойдёт не так. Добавить: checkpoint-коммит (или stash+тег) до создания ветки.
- «Поведенческий чек-лист» предлагаю фиксировать не прозой, а как smoke-сценарий CLI (init/configure/doctor/search/run на фейк-фикстурах) — иначе критерий «ничего не сломалось незаметно» не проверяем.
- Базовую линию фиксировать **по коду и тестам**, не по КБ (КБ уже содержит неточности — пример с `test_cli`).

### Этап 1. Рефакторинг ядра — самый недооценённый этап

Объём удаления автоотклика в цифрах (по фактическим тестам):

| Что удаляется | Код | Затронутые тесты (примерно) |
| --- | --- | --- |
| `browser.apply` / `reconcile` / `already_applied`-пути | `browser.py`, `hh.py:310-391` | ~20 из 27 в `test_browser`, ~10 из 22 в `test_hh` |
| `engine.send`/`reconcile`/`unknown`-сценарии | `engine.py:95-146` | ~20 из 29 в `test_engine` |
| `claim/finish/recover/attempts`, глобальная пауза | `store.py:110-139` | ~10 из 19 в `test_store` |
| `kind='success'`, строки «Пауза отправок», ретированные команды | `telegram.py:67-83` | ~8 из 25 в `test_telegram` |
| `HH_LIVE`, `SEND_INTERVAL`, resume-валидация | `config.py` | ~6 из 16 в `test_config`+`test_cli` |

Итого **~60+ тестов из 156** удаляются или переписываются, плюс чистка трёх подсистем. Это больше, чем любой другой этап плана, включая новые адаптеры. Рекомендую разбить этап 1 на три под-этапа, чтобы каждый заканчивался зелёным набором:
1. **1a** — чистое переименование `hh_agent` → `job_finder` (импорты, `pyproject.toml`, entry point, скрипты), без изменения поведения. Все 156 тестов зелёные. *(Выполнено 03.11.2026.)*
2. **1b** — удаление автоотклика (код + переписанные тесты). Набор зелёный (~95–100 тестов).
3. **1c** — миграция схемы (новый ключ, статусы, колонки, пилотная запись). Набор зелёный + тест миграции на копии живой БД.

**Нерешённые вопросы этапа:**
- **Глобальная пауза.** `paused` живёт только для гейта отправки ([job_finder/store.py:113](../../job_finder/store.py#L113), [job_finder/engine.py:97](../../job_finder/engine.py#L97)). После удаления отправки пауза мертва. Предлагаю **переопределить её как «пауза доставки в Telegram»** — она естественно закроет и будущий флаг `DELIVER` (этап 8), иначе флаг появится из ниоткуда.
- **Правило пропуска тестов.** `test_required` → `rejected` ([job_finder/rules.py:27](../../job_finder/rules.py#L27)) существовало, чтобы не тратить автоотклик. Без автоотклика это правило теряет смысл: пользователь откликается сам и сам решит, проходить ли тест. Нужно решение: оставить `rejected`, или понизить до информационной метки в карточке. План молчит.
- **31 запись `ready` в живой БД.** Письма сделаны старым writer'ом (без `score`/`resume_advice`). Решить: доставить как есть, перегенерировать после включения нового writer'а, или пометить. Плюс `Letter` при чтении из JSON должен иметь дефолты для новых полей ([job_finder/store.py:64](../../job_finder/store.py#L64)).
- Переименование ломает editable-установку `.venv` (нужен повторный `pip install -e .`) и entry point `job-finder`; корень проекта уже называется `job_finder_v2`, а пакет по плану — `job_finder`. Лучше согласовать имена (или оставить entry point стабильным).

### Этап 2. Протокол и реестр — хороший этап, но с пробелами

- **Переформулировать как извлечение из `hh.py`**: rate limiter, backoff, обновление токена, санитизация уже написаны и протестированы (22 теста). Новый `base.py` должен рождаться переносом, а не с нуля.
- **Контракт адаптера неполон.** Нужно добавить: `close()`/время жизни разделяемого HTTP-клиента; семантику `since` (по `published_at`? по водяному знаку последнего поиска?); **контракт отчёта о покрытии** (сегодня `search_report = {ids, pages, incomplete, notes}` — мультиплатформенная версия должна сохранить форму и агрегироваться в `/status`); формат хранения `last_search:<platform>` и синтаксис интервалов в `.env` (`SEARCH_INTERVAL=21600` — один на всех? или `SEARCH_INTERVAL_HH`?). План говорит «у каждой платформы свои last_search и интервал», но синтаксиса нет.
- **Главное скрытое решение: SQLite + asyncio.** Сейчас вызовы sqlite3 синхронные и выполняются в цикле событий; «платформы работают параллельно» упирается в блокировки соединения (timeout=10) и затормаживание event loop. Варианты: (а) один потребитель — адаптеры пишут в `asyncio.Queue`, ядро-потребитель один ходит в SQLite (рекомендую: минимум изменений, детерминизм сохранён); (б) `aiosqlite`; (в) `run_in_executor`. Выбрать нужно до этапа 3, иначе дедуп будет бороться с гонками.
- `RateLimited` с «повтором без потери состояния» — уточнить, где живёт таймер повтора (settings-ключ на платформу), чтобы рестарт не бомбил платформу сразу.

### Этап 3. Дедупликация

- **Схема не поддерживает заявленную логику.** «Записи с той же нормализованной компанией или тем же нормализованным названием» требуют индексированных `norm_company`/`norm_title` — их нет ни в `jobs`, ни отдельной таблицей. Нужна либо пара колонок, либо таблица `job_keys(job_id, norm_company, norm_title)`.
- **Точный ключ `(norm_company, norm_title)` опасен как мгновенное слияние**: один работодатель публикует несколько разных позиций с одинаковым названием («Python разработчик» ×N). План формулирует «проверку существующего кластера», но не говорит, что проверка обязана быть эмбеддинговой и для точного ключа. Рекомендация: точный ключ — только короткий путь к кандидатам; слияние — всегда через близость описания (или порог выше 0.93 для точного ключа + проверка описания).
- **SimHash ≠ cosine.** SimHash даёт Hamming-расстояние (близость Jaccard), порог 0.93 косинуса на него не переносится. Нужны два независимых порога в конфиге и отдельный отчёт о качестве в fallback-режиме (риск-таблица плана это признаёт качественно, но не метрически).
- **Версионирование эмбеддингов**: смена провайдера/модели делает хранимые векторы несравнимыми (другая размерность, другой смысл). Хранить `provider+model+dim` рядом с векторами; при смене — пересчёт всех эмбеддингов (тысячи запросов — учесть в стоимости).
- **Кросс-языковые дубли** (hh на русском vs RemoteOK на английском): многоязычные эмбеддинги справятся, SimHash — нет. Зафиксировать как известное ограничение fallback'а.
- **Таблица ссылок кластера**: этап 5 требует «все ссылки кластера» в карточке, но хранить их негде. Нужна `job_sources(job_id, source, native_id, url, published_at)` (или JSON в кластере). В схеме п. 2.4 её нет.
- **Политика слияния полей** при обновлении кластера не определена: чья зарплата каноническая при конфликте (gross/net, валюта), что с `remote`/`closed`, кто `rep_job_id`. Рекомендация: представитель — hh при наличии (самые структурированные данные), правила слияния — таблицей в ADR.
- Масштаб не проблема: единицы тысяч векторов считаются чистым Python без numpy (numpy сейчас не в зависимостях — осознанный выбор).

### Этап 4. Writer v2

- **Противоречие «один проход» vs два шага.** Цель этапа обещает один LLM-проход, а п. 2.1 и список файлов описывают два (`scoring.py` дешёвой моделью + `writer.py`). Решить явно. Рекомендация: **один проход дешёвой моделью** — письма короткие и шаблонные, вторая модель не окупается; если качество не устроит на приёмке (этап 8), добавить вторую модель письму.
- **P0: потеря дословной верификации.** Сегодня модель выбирает предложения, а код проверяет `text == _render(...)` ([job_finder/letters.py:106](../../job_finder/letters.py#L106)) — галлюцинация фактов невозможна конструктивно. Свободное письмо из LLM так не проверить; JSON-схема проверяет форму, не правду. План декларирует «факты только из профиля», не предлагая механизма. Варианты (нужно выбрать и записать в план):
  1. **Оставить конструируемые письма** — расширить библиотеку фактов и шаблонов; нулевой регресс безопасности (рекомендую как базовый).
  2. Свободное письмо + **второй проверочный проход** дешёвой моделью: каждая фактическая фраза письма сверяется с профилем, при расхождении — перегенерация/фолбэк.
  3. Свободное письмо + показ владельцу списка «утверждений для проверки», осознанный риск.
- **Советы по резюме**: модель должна видеть структуру резюме (секции), а не только факты — иначе советы «reorder summary» будут выдуманы. Энумы `section`/`action` закрыть (в плане стоят `...`). Требование «≥1 совет» принуждает модель выдумывать совет для идеального совпадения — разрешить 0 с причиной.
- **`prep_topics`** — то же: для идеального совпадения темы не нужны.
- **Журнал стоимости**: «учёт токенов и стоимости в журнале» — таблицы нет. Добавить `llm_calls(id, job_id, kind, model, prompt_tokens, completion_tokens, cost, created)` (или хотя бы JSON в settings — плохо: неудобно считать). И задать пределы повторных попыток при невалидном JSON (иначе ретраи сжигают бюджет).
- **Кэш скоринга** `(job_id, версия профиля)` — добавить `model` в ключ; механизм версии профиля не описан (дата файла? явная версия в JSON?).
- **Промпт-инъекция в скоринге**: вакансия как данные — правило должно действовать и для scoring-промпта, не только для writer'а.
- **Философия отбора**: одобренный дизайн (19.10) говорит «неполное соответствие не блокирует отклик». Вердикт `apply|skip` скоринга это меняет. Рекомендация: по умолчанию скоринг **информационный** (оценка и причина в карточке), `skip` — только выше явного пользовательского порога; порог в конфиге, по умолчанию выключен.
- `profile.json` переносится в `profile/facts.json` — не забыть `package-data` в `pyproject.toml` и путь в конфиге.

### Этап 5. Telegram

- **`DELIVER` флаг**: используется в этапе 8, но в конфиг не введён. Ввести в этапе 1/5 (см. выше про переопределение паузы) и описать семантику: `false` → карточки копятся в `ready`; `true` → outbox-доставка.
- **`/skip` без механики**: «занести в отсев» — чем? Естественный механизм: `decide(rejected, "Пропущена пользователем")` — поиск не вернёт запись повторно (`INSERT OR IGNORE` по `source:native_id`), статус терминальный. Либо отдельная таблица, если нужна возможность отмены. Выбрать и записать.
- **`/letter source:native_id`**: текущий парсинг только цифры ([job_finder/telegram.py:130](../../job_finder/telegram.py#L130)); `:1` в командах Telegram не конфликтует с сущностями, но regex и вывод `/history`, `/clarifications` нужно переделать под теги источников.
- Шаблон карточки (заголовок+зарплата+все ссылки+оценка+письмо+советы+темы) почти гарантированно > 4096 символов — чанкинг уже есть ([job_finder/telegram.py:36](../../job_finder/telegram.py#L36)), но стоит подумать о **HTML-формате** (ссылки кликабельны, меньше ограничений на длину в одном сообщении не будет, но читаемость выше) и о том, что preview сейчас глобально выключен ([job_finder/telegram.py:222](../../job_finder/telegram.py#L222)).
- `STATUS_LABELS` ([job_finder/telegram.py:23](../../job_finder/telegram.py#L23)): добавить `read`/`delivered`, убрать `sending`/`sent`/`unknown`.
- **Формат доставки** (открытый вопрос 2) влияет на этап: немедленный режим при 20–50 новых вакансиях за цикл — заливка чата. Рекомендация в разделе 8.

### Этап 6. Адаптеры

Чек-лист плана хорош. Дополнить:
- **Приоритет кандидатов по риску**: Habr Career (публичный JSON+RSS, без входа) и RemoteOK (открытый API, без входа) — самые дешёвые и безопасные; Djinni/getmatch — вход и серая зона ToS; GeekJob — парсинг; LinkedIn — только ручной экспорт (план это уже признаёт). Рекомендую пилот дедупа валидировать на hh+Habr+RemoteOK.
- В чек-лист добавить: время жизни HTTP-клиента; контракт отчёта покрытия; ISO-нормализацию `published_at` (у RemoteOK дат может не быть); переиспользование `parse_salary` из `rules.py` для текстовых зарплат; политику фикстур (минимум: листинг, полная вакансия, 429/капча/ошибка) — как в текущих тестах.

### Этап 7. Эксплуатация

- **Логирование**: в проекте вообще нет файла лога — только stdout. Для постоянно работающего агента добавить ротируемый `.state/agent.log` (иначе отладка «почему Habr молчит 3 дня» невозможна). Этого пункта нет нигде в плане.

- Выверка КБ против кода (примечание пользователя о неактуальности КБ) — отдельный пункт этапа 7.

### Этап 8. Приёмка

- Ручная проверка 20–30 кластеров проверяет только **ложные слияния**. Добавить проверку **ложных пропусков** (одна вакансия пришла дважды из разных источников как разные карточки) — это несимметричная, не менее важная метрика.
- Замер стоимости должен включать **эмбеддинги** (и их кэш-промахи), а не только скоринг/письма.
- `DELIVER=false` — первый прогон должен быть на копии БД, чтобы не размечать живые 1690 записей.
