# Первый живой запуск мультиплатформенного агента (06.11.2026)

Запуск агента на живой БД после этапов 0–7. Фиксирует фактическое поведение,
найденные и исправленные дефекты, и текущее состояние приёмки (этап 8).

## Хронология

1. **Миграция живой БД**: при первом `run` БД автоматически мигрировала
   v3→v4 (`job_finder/migrate.py`): бэкап в `.state/backups/`, 1690 строк
   сохранены, архив `application_history` (3 строки), статусы отправки →
   `skipped`/`needs_clarification`, 31 `ready`-строка получила снимок
   `legacy_letter` и `rules_version='legacy'`.
2. **Дефект №1 — `legacy_letter`**: `Vacancy.from_dict` не ожидал служебного
   ключа в data старых строк → `TypeError` при уведомлении. Исправлено:
   служебные ключи (`possible_duplicates`, `legacy_letter`) извлекаются до
   конструирования модели; уведомления/подготовка фильтруются по включённым
   источникам (строки отключённого hh не трогаются до включения).
3. **Дефект №2 — колонка `source`**: `round_commit` не проставлял источник
   новых строк (оставался дефолтный `hh`). Исправлено в коде + разовая
   правка 53 строк живой БД.
4. **Дефект №3 — `BUTTON_DATA_INVALID`**: кнопка карточки клала полный
   `source:native_id` в `callback_data`; у WWR slug >64 байт → Telegram 400,
   очередь доставки блокировалась, карточки по кнопке не приходили.
   Исправлено: `callback_data = 'c:<id строки outbox>'` (короткий), вакансия
   берётся из outbox; старый формат `card:<id>` поддерживается.

## Уроки (в beads-память тоже записаны)

- callback_data inline-кнопок Telegram — лимит 64 байта.
- Telegram (Bot API и MTProto) с этой машины требует VPN; без него
  источники уходят в `waiting`/`next_retry` и раунд возобновляется сам.
- Перезапуск агента снимает паузу доставки (проблему исправили → запустили).
