# 06. Telegram-интерфейс

Роль Telegram: **только отчёты владельцу**. Управление работой (запуск/остановка, режим, пауза) — только на компьютере. Новые сообщения не содержат кнопок; бот отвечает на текстовые команды по запросу.

## Команды

| Команда | Ответ |
| --- | --- |
| `/status` | Работает ли скрипт, блокировка доступа к HH и её причина, режим (просмотр/реальная отправка), пауза, счётчики очереди по статусам, результат последнего поиска (ID, страницы, полнота охвата) |
| `/clarifications` | Первые 20 вакансий на уточнение: ID, название, причина, ссылка |
| `/clarifications N` | Страница N списка уточнений (по 20) |
| `/history` | Последние 20 результатов (sent/rejected/closed/error/unknown) с причинами + сводка счётчиков |
| `/letter 123456` | Точный текст письма, использованные факты, добавленные утверждения и план подготовки (только для владельца) |
| `/help` | Краткая справка |

Устаревшие команды `/search`, `/pause`, `/resume`, `/reconcile`, `/requeue`, `/queue`, `/settings` получают ответ «эта команда больше не управляет работой…» и ничего не меняют.

## Привязка владельца (`pair`)

1. Команда `python -m job_finder pair` генерирует одноразовый код и просит отправить боту `/start <code>` из личного чата (5 минут на это).
2. Принимается только сообщение: личный чат, `from.id == chat.id`, не бот, текст `/start <code>`.
3. `TELEGRAM_OWNER_ID` сохраняется в `.env`; offset переносится в `settings.telegram_offset`; в outbox кладётся приветствие.
4. Перед привязкой проверяется отсутствие webhook (иначе конфликт поллеров).

## Модель доступа

- Только владелец в личном чате (`_authorized`): тип ID — целое, `sender.id == owner_id == chat.id`, `chat.type == 'private'`, `sender.is_bot == False`.
- Все прочие сообщения игнорируются (записываются как `ignored`), чужой пользователь ничего не узнаёт; даже callback-квитирование не раскрывает данных.

## Механика доставки

- **Polling**: `getUpdates` с long polling 30 с, `allowed_updates = ["message", "callback_query"]`; обновления сортируются по `update_id`.
- **Дедупликация**: каждая команда пишется в `inbox` (PK `update_id`) и продвигает `telegram_offset`; повторно доставленное обновление не вызовет повторного ответа; offset никогда не откатывается назад.
- **Старые кнопки**: нажатие кнопки в ранее отправленном сообщении → пустой `answerCallbackQuery` и попытка снять клавиатуру именно этого сообщения (`editMessageReplyMarkup` с пустой клавиатурой). Массовое удаление старых клавиатур невозможно — их message_id не сохранялись.
- **Outbox**: автоматически отправляются только `reply` (ответы на команды) и `success` (подтверждённые отклики с письмом, утверждениями и подготовкой). Справочные события (`event`) не рассылаются проактивно — они доступны через `/status` и `/history`.
- **Чанки**: сообщение режется на части ≤4000 UTF-16 юнитов (без разрыва суррогатных пар); прогресс чанка персистится в `settings.telegram_chunk_<id>`.
- **Rate limit**: интервал между сообщениями ≥1.05 с; при 429 — пауза на `retry_after` (1–3600 с).
- **Устойчивость**: сбой сети Telegram → пауза 30 с и повтор; работа с HH продолжается; редкий сбой после доставки может продублировать один чанк уведомления, но не отклик.

## Автоматические уведомления

Единственное автоматическое сообщение — **подтверждённый успешный отклик**: ссылка на вакансию, причина, точный текст письма, добавленные утверждения (только для владельца), темы подготовки. Уточнения, ошибки и дневные сводки автоматически не отправляются — они доступны по командам.

## Ограничения

- Пока скрипт не запущен, бот не отвечает (всё в одном процессе).
- После длительного простоя (≈неделя) Telegram может изменить последовательность update_id; если команды перестали приниматься — остановить приложение и повторить `pair`.
- Один бот = один поллер: не запускать параллельно другие программы с polling/webhook для этого токена.
