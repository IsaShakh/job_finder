# 07. Модель безопасности и ограничения

Проект сознательно строится вокруг принципа «личный агент на личном компьютере, минимум доверия внешнему миру».

## Секреты и файлы

- `.env` — токен Telegram, ключ LLM; создаётся с правами 0600, ввод скрыт (`getpass`), значения записываются без интерполяции (`quote_mode="always"`), права перевыставляются после записи. В Git исключён.
- `.state/` — база, блокировка, профиль браузера; каталог 0700, БД 0600.
- `.cache/ms-playwright` — локальный Chromium (не системный браузер, сессия не пересекается с браузером пользователя).
- Валидация конфигурации не выводит значения секретов в ошибках; `Config` помечает токен и ключ `repr=False`.
- Текст исключений не выводится в CLI, кроме санитизированных: общие исключения печатаются только именем типа (`type(exc).__name__`) — в сообщениях могут быть URL запросов или текст страниц.
- Ошибки Telegram/модели обёрнуты в `TelegramError`/`LetterError` без токенов, URL и тел ответов.

## Границы доступа к hh.ru

- `safe_hh_url` допускает только `https://hh.ru` и `*.hh.ru`, без username/password, порт только 443. Любой другой адрес → `AttentionRequired`.
- **Только публичная навигация по сайту** (страницы поиска, вакансий, формы отклика). Никаких приватных эндпоинтов, скрытых методов, экспорта cookies или чужих браузерных сессий.
- Обход капчи не применяется: капча/ограничение/вход → пауза и сообщение владельцу.
- Вход в HH — руками пользователя в отдельном окне (`login`); сессия хранится в постоянном профиле `.state/browser-profile`, никуда не экспортируется.
- Выбор резюме — по ID согласованного резюме; профиль и видимость резюме приложение не меняет.

## Защита от повторной отправки

- Намерение фиксируется в БД до клика (`claim`: `ready → sending`, запись в `attempts`).
- Один клик, затем только ожидание подтверждения; появление «Откликнуться повторно» не ведёт к новому отклику.
- После клика любой сбой → `unknown`, пауза; автоматический повтор невозможен, сверка только по явному подтверждению «Вы откликнулись» на странице вакансии.
- Уже отправленный отклик (в т.ч. вручную) распознаётся до формы и фиксируется как `sent`.

## Prompt injection и честность писем

- Данные вакансии рассматриваются как **недоверенные**; модель явно инструктируется игнорировать инструкции в них.
- Модель выбирает только из неизменяемых фактов профиля и закрытого списка утверждений о технологиях; текст письма дословно пересобирается локально и сравнивается (`text == _render(...)`), иначе отказ.
- Выдумывание карьерных фактов (должности, даты, образование, достижения) исключено валидацией.
- Заголовок вакансии не может попасть в письмо как факт (используется только валидированный числовой URL).
- Добавленные утверждения хранятся отдельно, не превращаются в факты профиля, показываются только владельцу.

## Целостность очереди и конкурентность

- Один процесс: `fcntl.flock` на `.state/agent.lock`.
- SQLite WAL + транзакции: `claim`/`finish`/`make_ready` атомарны; два соединения не могут отправить одну вакансию.
- `decide` не перезаписывает терминальные статусы `sent/sending/unknown`.
- `finish(sent)` требует непустого `evidence`.
- Восстановление после краха: `sending → unknown` (никогда не «не отправлено»), `ready` без письма → `found`.

## Границы, которые проект не пересекает

- Не изменяются резюме, настройки аккаунта HH, видимость резюме.
- Не отправляются сообщения работодателям помимо отклика (чат не используется).
- Не регистрируются приложения-работодатели вместо соискательских.
- Нет автоматического чтения входящих сообщений работодателей.
- Нет автоматической обработки «уточнений» — решения с неоднозначными условиями ждут человека.
