## 1. Цель и рамки

Один локальный асинхронный Python-процесс: собирает вакансии с выбранных площадок, убирает дубли между ними, фильтрует по согласованным правилам, готовит карточку (и, по решению по V1-объёму, письмо + советы по резюме) и присылает в Telegram. **Пользователь откликается сам.**

**Исключено:** автоотклик целиком (браузерная отправка, `HH_LIVE`, `resume_id`, `attempts` как активная таблица, статусы `sending`/`sent`/`unknown`, капча при отправке, `send_interval`); обход капчи и скрытые методы; деплой на сервер; выдумывание фактов.

**Явное исключение из «скрытых методов»:** программный API hh.ru в стиле официального Android-приложения (решение 30.10.2026, [ресёрч](../research/2026-10-30-programmatic-api.md)). Способ доступа не является публично документированным API — риск отзыва ключей/блокировки принимается осознанно, браузерный фолбэк удаляется вместе с Playwright (решение зафиксировано в этапе 1b).

**Свойство продукта (не баг):** пока компьютер спит/выключен, сбор не идёт и бот не отвечает; обновления Telegram хранятся ≤24 ч. Для круглосуточной работы нужен сервер — вне объёма.

## 3. Архитектура

Пакет `job_finder/`: `__main__.py` (CLI: init, configure, pair, doctor, run), `config.py`, `models.py`, `store.py`, `rules.py`, `dedupe.py`, `scoring.py`, `writer.py`, `llm.py`, `engine.py`, `telegram.py`, `adapters/` (`__init__.py` — реестр, `base.py`, `hh.py`, далее платформы).

Конвейер:

```
 адаптеры (параллельно, в рамках раунда `/search`)
   search → SearchReport (hits + incomplete + notes)   [отчёт покрытия сохраняется]
        │
   отсев известных по базе (без дублей строк) + last_seen  [водяной знак коммитится атомарно с сохранением строк — 16.5]
        │
   fetch → каноническая Vacancy
        │
   дедупликация: точный ключ → кандидаты → эмбеддинги   [консервативно, см. раздел 8]
        │
   жёсткие правила (детерминированно, без LLM)
        │
   LLM-скоринг (информационный: оценка + причина)       [не блокирует]
        │
   writer: письмо + советы (сбой НЕ блокирует карточку)
        │
   outbox → Telegram (уведомление с кнопкой + уточнения)
```

**SQLite + asyncio (решено 05.11.2026, R8):** адаптеры параллельны, но в SQLite пишет **один потребитель** через `asyncio.Queue`; соединение — **`aiosqlite`** (очередь + отдельный поток на соединение, event loop не блокируется), WAL остаётся. Повтор `RateLimited` — по персистентному таймеру на источник (`settings: next_retry:<source>`), чтобы рестарт не бомбил площадку.

**Запуск поиска — вручную** (решено 03.11.2026; контракт раунда R5 — 05.11.2026, раздел 16.5): автоматических интервалов нет. Раунд запускается командой `/search` в Telegram (или CLI `search`); все источники опрашиваются параллельно. `since` следующего раунда — `t_start` предыдущего (обход с перекрытием + дедуп; позиция пагинации не персистится). Сбой одной платформы изолирован (`AttentionRequired` паузует только её).

## 4. Каноническая модель (исправления из рецензий)

Обе ошибки черновика устранены: PEP 604-синтаксис заменён на `Optional[...]` (стек: **Python 3.12+** — решено 05.11.2026: 3.9 EOL 31.10.2025, 3.10 EOL 01.10.2026), поле без значения по умолчанию больше не стоит после полей со значениями. Добавлены явные поля для критериев (значение «неизвестно» сохраняется как `None`):

```python
from typing import Optional
from dataclasses import dataclass, field

@dataclass(frozen=True)
class Vacancy:
    source: str                    # "hh", "remoteok", ...
    native_id: str
    url: str                       # строит адаптер; ядро URL не собирает
    title: str
    company: str                   # очищенное название
    description: str
    requirements: str
    salary: Optional[Salary] = None          # minimum, maximum, currency, period, raw
    remote: Optional[bool] = None            # None = не подтверждено
    remote_geo: Optional[str] = None         # география удалёнки («только РФ», «из ЕС»…)
    location: Optional[str] = None           # город/страна офиса (для релокации: «Москва», «Дубай»…)
    timezone: Optional[str] = None
    employment: Optional[str] = None         # занятость
    salary_gross: Optional[bool] = None      # налоговый режим зарплаты
    published_at: Optional[str] = None
    closed: bool = False
    language: str = "ru"
    raw: dict = field(default_factory=dict)  # отладочный снимок платформы
```

## 5. Схема БД (целевая)

- `jobs` — ключ `id = source:native_id`; **каждая публикация источника — отдельная строка**; добавляются `source`, `published_at`, `cluster_id`, `last_seen`, `last_read`, `norm_company`, `norm_title` (индексированы — для кандидатов дедупа), `content_hash` (хэш описания/требований), `test_required`, `grade`/`grade_evidence`, `skills` (JSON), `rules_version`, `profile_version` (версии на момент решения), `manual_decision` (`keep`/`skip`/NULL), `manual_decision_at`; удаляются `resume_id`, `evidence`, `attempts`.
- `clusters(id, rep_job_id, centroid BLOB, embedding_model TEXT, embedding_dim INT, created, status TEXT, skipped_at TEXT)` — группа дублей; представитель — hh при наличии; `status` — кластерное ручное решение (`none`/`skipped`), раздел 16.3.
- `job_embeddings(job_id PK, embedding BLOB, model TEXT, dim INT, content_hash TEXT)` — векторы **версионированы** по модели и содержимому: смена провайдера/модели или изменение текста → новый вектор (R7).
- `llm_calls(id, job_id, kind, model, prompt_tokens, completion_tokens, cost, created)` — журнал стоимости.
- `application_history(...)` — **архив** истории откликов текущей версии (бывшие `attempts` + `sent`/`unknown`); не участвует в новых статусах.
- `settings`, `inbox`, `outbox`, `skip_events` — не «без изменений»: в `outbox` добавляются `job_id`/`cluster_id` и новый `kind` карточек; `settings` получает по-платформенные ключи (`last_search:<source>`, `search_report:<source>`, `next_retry:<source>`, `rules_version`, `profile_version`, `DELIVER`, `NOTIFY_MODE`, `TG_CHANNELS`). Уникальность карточки — по кластеру: частичный уникальный индекс `(cluster_id)` для `kind='card'`.
- Статусы: `found` (сохранена, не обработана), `read` (карточка открыта), `rejected` (автоматический отказ правилами/скоринг-порогом, с причиной и `rules_version`), `skipped` (ручной `/skip` — терминален, пересматривается только явной отменой), `needs_clarification`, `ready` (карточка готова, ждёт доставки), `delivered`, `closed`, `error`. Терминальные: `skipped`, `closed`; `rejected` автоматически пересматривается при смене `rules_version`/`profile_version`; остальные не терминальны. Жизненный цикл — раздел 16.2.
- **`/skip` действует на весь кластер**: `clusters.status='skipped'` + все строки кластера → `skipped` (причина «пропущена пользователем»); будущие публикации того же кластера сразу получают `skipped` — иначе вакансия вернётся с другой площадки.

## 6. Протокол адаптера

```python
class SourceAdapter(Protocol):
    name: str
    def __init__(self, config): ...
    async def search(self, criteria, since) -> SearchReport   # hits + incomplete + notes
    async def fetch(self, key) -> Vacancy
    async def close(self): ...                                # время жизни HTTP-клиента
```

`search` возвращает дешёвые поля листинга **и признак полноты покрытия** (как текущий `search_report.incomplete` — не терять при рефакторинге); `since` — по `published_at`/водяному знаку платформы. `fetch(key)` получает **`native_id`** (источник фиксирован контекстом адаптера); `published_at` — **ISO-8601 в UTC** (нормализует адаптер). Пагинация, аутентификация, лимиты, парсинг — внутри адаптера. Исключения: `AttentionRequired` (нужен человек), `RateLimited` (повторить позже), `VacancyUnavailable` (закрыта/удалена). Общие хелперы `adapters/base.py` **извлекаются из текущего `job_finder/hh.py`** (rate limiter 0.4 с, обновление токена, санитизация ошибок, пагинация — уже написаны и покрыты 22 тестами), а не пишутся заново. Идентичность и прогресс по экземплярам источников — раздел 16.1.

Токены платформ: `.state/tokens/<platform>.json` (0600).

## 7. Правила отбора (v3, 03.11.2026)

**Регион источника** задаёт адаптер по умолчанию (`RU`/`intl`): hh, Habr Career, русскоязычные каналы → `RU`; RemoteOK, We Work Remotely, зарубежные каналы → `intl`. **Факты вакансии важнее дефолта источника (R1, 05.11.2026):** `evaluate(vacancy)` прогоняется по **всем активным профилям** из конфига; вакансия проходит, если проходит любой, причина помечает профиль. Реализация: `evaluate(vacancy, profile)`.

Общие для всех регионов:

- **Python обязателен** в названии/описании/требованиях (как сейчас); нет → `rejected`.
- **Валюта не конвертируется**: зарплата в карточку отдаётся в исходной валюте (AED/USD/EUR/RUB…); RUB-порог применяется только к зарплатам в RUB.
- **Явный Junior/Trainee/стажёр** без подходящей зарплаты → `rejected` (правило уровня сохраняется).
- **Командировки** (для `RU`): упоминание → `rejected`, «без командировок» не считается.
- **Скоринг информационный**: оценка 0–100 = «соответствие» (выше — лучше); идёт в карточку с причиной; опциональный отсев (по умолчанию выключен) действует **ниже** явного порога в конфиге. Оценка — не вероятность трудоустройства.
- Правило пропуска тестов: после удаления автоотклика — **информационная метка в карточке** (решено 05.11.2026; `rejected` за тест не применяется).

### 7.1 Россия (регион RU)

- **Формат**: удалёнка ИЛИ релокация/офис в **Москве** (уточнение 03.11.2026; R1 — 05.11.2026).
  - `remote=True` + `remote_geo` «только РФ»/не указано → подходит; `remote_geo` ограничивает чужой территорией (US-only, EMEA, «outside the US» и т.п.) → `rejected` (право на работу не предполагается);
  - локация содержит **Москву** (офис/гибрид) → подходит, метка «офис/гибрид, Москва»; «Московская область»/«Подмосковье» вычитаются стоп-паттернами (N10), «Москва и МО» — подходит;
  - **релокация считается только с целевым городом**: «релокация в Москву»/«relocation to Moscow» → подходит; «relocation» без города → `needs_clarification`; в другой город → `rejected` (N13);
  - `remote=None`, Москвы нет → `needs_clarification`;
  - `remote=False`, Москвы нет → `rejected`.
- **Поиск по hh идёт двумя ветками** с дедупом между ними: удалёнка (`schedule=remote`) + Москва (`area=1`, с учётом релокации). У Habr/каналов фильтрация по локации не применяется — решает правило выше.
- **Зарплата в RUB**: порог **150 000 ₽/мес**; единая таблица решений — раздел 7.3 (R9, 05.11.2026).
- **Если зарплата не указана ИЛИ валюта ≠ RUB** — берём в очередь при выполнении любого из:
  1. явный **грейд Middle+** (Middle/Mid/Senior/Lead/Principal/Staff/ведущий/тимлид/техлид); или
  2. **грейд не указан** (напр. «Python-разработчик», «Backend-разработчик») **+ Python-стек** в вакансии (FastAPI, Django, Flask, asyncio, SQLAlchemy, pytest и т.п.; слово «Python» в названии тоже считается) → берём.
  - Иначе → `rejected` («грейд и Python-стек не подтверждены»).
- Фиксированная зарплата или верхняя граница ниже порога в RUB → `rejected` независимо от грейда/стека; «от X без верхней границы» — **не** «явная зарплата ниже порога» (7.3).

### 7.2 Дубай и зарубежные вакансии (регион intl)

- **Формат**: удалёнка ИЛИ релокация/офис в целевом регионе (Дубай) — `remote=True` + `remote_geo` «worldwide»/не указано → подходит; `remote_geo` с чужой территорией (US-only, EMEA) → `rejected`; локация/`remote_geo` содержит Дубай или «релокация в Дубай» → подходит; «relocation» без города → `needs_clarification`; релокация в другой город → `rejected`; ничего не указано → `needs_clarification` (R1, 05.11.2026).
- **Зарплата**: порог не применяется (любая), валюта отдаётся как есть, без пересчёта.
- **Грейд**: от Middle и выше; грейд не указан → как в RU: проверяем Python-стек, есть → берём; нет → `rejected`. Явный Junior/Trainee → `rejected` независимо от зарплаты (**приоритет регионального правила над общим**, R9).
- Категории: обязательные (Python, формат, регион) / предпочтения (стек, отрасль, размер компании — влияют на порядок выдачи и объяснение) / неизвестные (зарплата, гео, грейд — обрабатываются правилами выше, ничего не теряется молча).

### 7.3 Единая таблица зарплатных решений (R9, 05.11.2026)

Одна таблица «регион × валюта × период × формат вилки × грейд». Неразобранная сумма/валюта ≠ полноценная иностранная зарплата; исходная строка зарплаты и причина решения сохраняются.

## 8. Дедупликация (консервативная)

Принцип: **для личного поиска лучше редкий повтор, чем потерянная вакансия.**

- Нормализация названия/компании: регистр, пунктуация, «Senior»/«Сеньор», юрформы.
- Точный ключ `(norm_company, norm_title)` — **один из трёх источников кандидатов**, не слияние (одна компания может искать двух Python-разработчиков в разные команды). Кандидаты = точный ключ ∪ **прямые ссылки в тексте** (`hh.ru/vacancy/<id>`, `habr.com/.../vacancies/...` — жёсткое доказательство тождества) ∪ **эмбеддинг-top-K** (K=5 ближайших среди активных строк за последние 30 дней — ловит кросс-языковые пары, которых точный ключ не видит).
- Сравнение — эмбеддинги по «название + компания + требования (`requirements`)»; при пустых требованиях — первые ~800 символов описания с вычищенными шаблонными блоками («о компании», «мы —» и т.п.); порог косинуса ~0.93 — **гипотеза**, подбирается на размеченных примерах. Требования первичны: у двух команд одного работодателя они различаются — это признак «не сливать».
- SimHash-fallback — **со своим порогом** (Hamming ≠ cosine); кросс-языковые дубли (hh ru vs RemoteOK en) fallback не ловит — фиксируется в отчёте.
- Сомнительное совпадение **не объединяется автоматически** (показывается отдельно с пометкой «возможно, дубль»). Правила оценивают **каждую публикацию кластера — кластер проходит, если проходит хотя бы одна** (широкий охват; причина указывает источник); карточка строится из всех записей кластера, конфликты показываются по источникам. Полная таблица решений кластера — раздел 16.3.
- Конфликты полей кластера **не затираются**: зарплата/география/описание каждого источника сохраняются; политика слияния — таблицей в ADR.
- Повторное чтение: `last_seen`/`last_read`, детект изменения описания (хэш), переоценка не-терминальных записей при смене профиля/критериев, повторы после временных ошибок по таймеру.

## 9. LLM: скоринг, письмо, советы

- **Один проход дешёвой моделью** (решено 03.11.2026): один вызов возвращает оценку соответствия + письмо + советы по резюме. Вторая (сильнее) модель для писем — только если приёмка этапа 8 покажет слабое качество. **Независимые результаты (R10, 05.11.2026):** ответ `{score, score_reason, letter_blocks, advice[]}` валидируется **по частям** — невалидное письмо не выбрасывает корректный скоринг; статусы трёх артефактов хранятся отдельно (`ok`/`unavailable`/`failed`/`pending`); приватные рекомендации — отдельные поля, конструктивно не участвуют в сборке письма.
- **Верификация фактов — конструируемое письмо** (решено 03.11.2026, вариант (а)): модель выбирает одобренные фразы профиля, код дословно сверяет собранный текст (механика текущего `letters.py`); карьерные факты (должности, даты, образование, достижения, цифры) **никогда не выдумываются**.
- **Технологии, которых нет в резюме**: не упоминаются, **кроме случая, когда вакансия их явно требует** — тогда добавляется «ограниченное утверждение» о практическом знакомстве из закрытого списка с планом подготовки; показывается только пользователю, в письмо работодателю не попадает и фактом профиля не становится.
- Совет по резюме: каждый пункт имеет основание (какой пункт вакансии его вызвал + какой реальный опыт позволяет).
- «Минимум один совет» и «2–3 темы» — **не обязательны**: для идеального совпадения допускается 0.
- **Кэш с версией содержимого (R7, 05.11.2026):** скоринг — хэш `(job_id, content_hash, rules_version, profile_version, модель, версия промпта)`; письмо/советы — хэш `(cluster_id, хэш требований кластера, profile_version, модель, версия промпта)`. Изменились требования/описание → новый эмбеддинг + новая оценка + новое письмо; изменились только зарплата/гео → обновление карточки **без** нового письма.
- Промпт-инъекция: вакансия — данные, не инструкции (и для скоринга, и для writer'а); вывод валидируется схемой; ретраи при невалидном JSON ограничены (2) и попадают в `llm_calls`.
- Сбой письма **не блокирует уведомление/карточку**; бюджет ожидания LLM — timeout 30 с + 2 ретрая; исчерпан → карточка уходит без письма («письмо не подготовлено (причина)»), письмо/советы дозаполняются в фоне; кнопка открывает карточку из БД с тем, что уже готово (R10).

## 10. Telegram

- **Уведомление на каждую релевантную вакансию**: короткое сообщение «Нашлась новая релевантная вакансия: <название> — <компания>» + **inline-кнопка** «Посмотреть вакансию и письмо». По нажатию бот присылает полную карточку: должность, компания, зарплата (в исходной валюте), формат/локация, причина соответствия, все ссылки кластера, оценка + причина, сопроводительное письмо, рекомендации по резюме, темы подготовки.
- Кнопки **возвращаются** в интерфейс (в старом hh-агенте они были убраны); механика callback уже есть в текущем коде (`callback_query`, `answerCallbackQuery`, снятие клавиатуры).
- Сбой генерации письма **не блокирует уведомление**: в карточке — «письмо не подготовлено (причина)».
- Режим «сводка топ-N за цикл» — опция конфига (`NOTIFY_MODE=immediate|digest`, по умолчанию `immediate`), на будущее.
- `needs_clarification` — отдельным коротким сообщением; ручное решение командами **`/keep`** (одобрить → `ready`) и **`/skip`**; ответ сохраняется в `manual_decision` + `manual_decision_at` и никогда не перезаписывается автоматикой.
- Команды: `/search` (запуск раунда поиска по всем источникам), `/status` (состояния платформ и очереди, результат последнего раунда), `/history`, `/letter source:native_id`, `/skip source:native_id` (по кластеру), **`/keep source:native_id`**, **`/unskip source:native_id`** (явная отмена ручного пропуска кластера), `/help`. Управление возвращается в Telegram (в старом hh-агенте управляющие команды были убраны). `STATUS_LABELS` обновить (`read`/`delivered`/`skipped` вместо `sending`/`sent`/`unknown`).
- Outbox — единственный путь наружу: связь с `job_id`/`cluster_id`, защита от повторного создания одного уведомления, подтверждение отправки, учёт чанков (механика `telegram_chunk_<id>` уже есть). **Exactly-once не гарантируется**: редкий сбой после sendMessage может продублировать один чанк — допустимо, фиксируется в документации.
- `DELIVER` флаг в конфиге (false → уведомления копятся в `ready`); глобальная пауза переопределяется как **пауза доставки**.

## 12. Миграция данных (контракт R6, утверждён 05.11.2026)

**Порядок и атомарность:**

1. Свежий бэкап через `Connection.backup()` (WAL-безопасный) **перед первым изменением данных**; бэкап от 21.10.2026 не считается достаточным (отстаёт от живой БД).
2. Миграция — идемпотентные шаги, каждый проверяет маркер выполнения; `PRAGMA user_version` (3→4) повышается **последним шагом**, только после успешных проверок количества и содержимого.
3. Прерывание до повышения версии → повторный запуск продолжает с того же шага, архив не дублируется; после повышения — БД считается перенесённой, откат только восстановлением из бэкапа.
4. Старые таблицы/колонки (`attempts`, `resume_id`, `evidence`) удаляются **после** проверенного переноса в архив. Этап 1b удаляет активный **код** отправки; физическое удаление **данных** — только в 1c.

**Карта переходов «старое состояние → архив → активное»:**

## 13. Приёмка (4 результата)

1. **Пользователь считает выдачу полезной** — ручная оценка доставленных карточек и понятности причин отбора.
2. **Подходящие вакансии не теряются в отсеве** — проверка части отклонённых, неоднозначных случаев и ошибочных объединений.
3. **Перезапуск продолжает обработку** — прерывание на разных этапах: сохранённые данные, очередь, позиция поиска (водяной знак).
4. **Сбой одного источника/Telegram не останавливает остальное** — временная недоступность, 429, восстановление.

Дополнительно: стоимость LLM за цикл (с эмбеддингами), полнота охвата источников, поведение после длительного простоя.

## 16. Утверждённые контракты ядра (05.11.2026)

Закрывают замечания рецензии R1–R10 и находки перекрёстного анализа N1/N2/N5/N6/N8/N10–N13. R1 — раздел 7; R7/R10 — раздел 9; R8 — раздел 3; R9 — раздел 7.3; R5 — раздел 16.5; R6 — раздел 12.

### 16.1 Идентичность источников и прогресс (R2)

- **Идентичность публикации:** `source` — экземпляр источника: `hh`, `remoteok`, `habr`, `wwr`; для Telegram — **`telegram:<channel_id>`** (канал = экземпляр), `native_id` — `message_id`. Полный ID = `source:native_id`, парсинг — по первому `:` (см. `/letter`, `/skip`). Один класс адаптера `telegram_channels`, несколько экземпляров по конфигу `TG_CHANNELS` (поле `region` на канал: `RU`/`intl`).
- **Прогресс по экземпляру:** `last_search:<source>`, `search_report:<source>` (полнота покрытия), `next_retry:<source>` — на каждый канал отдельно. Сбой одного канала не двигает указатели других; `AttentionRequired` паузует только свой экземпляр. Прогресс продвигается **только после сохранения строк** этого источника (граница R5/N1).
- **Первый запуск канала:** читаются последние `TG_FIRST_READ_LIMIT=50` постов; отчёт помечается `incomplete: история канала не читалась полностью`; новый канал не наследует позицию старых.
- **Перекрытие и правки:** каждый раунд читает с перекрытием `TG_OVERLAP=5` известных постов; у известного поста сверяется `content_hash`: изменился → переоценка строки (раздел 8), нет → только `last_seen`. Правки старше окна не ловятся — допустимо, документировано.

### 16.2 Жизненный цикл вакансии (R3)

**Статусы и терминальность:** терминальные — `skipped`, `closed`; `rejected` — автоматическое решение, пересматривается при смене `rules_version`/`profile_version`; остальные не терминальны. Доставка карточки не запрещает обновление её данных.

**Переходы:**

| Событие | Переход |
| --- | --- |
| новая публикация | → `found`, затем сразу правила |
| правила прошли | → `ready` (карточка + письмо/советы) |
| правила отклонили | → `rejected` (+ причина, `rules_version`) |
| неоднозначно | → `needs_clarification` (+ причина) |
| доставлено в Telegram | `ready` → `delivered` |
| кнопка нажата | `delivered` → `read` |
| `/skip` (кластер) | все строки кластера → `skipped`; `clusters.status='skipped'` |
| `/unskip` | `clusters.status=NULL`; строки → переоценка |
| `/keep` | `needs_clarification` → `ready`; `manual_decision='keep'` |
| данные изменились (`content_hash`) | не-терминальные → переоценка; у `delivered`/`read` карточка в БД обновляется, **повторное уведомление не шлётся** |
| закрыта на площадке | → `closed` |
| сбой обработки | → `error`; повтор по таймеру/следующему раунду |

**Происхождение решения:** `reason` + `rules_version`/`profile_version` фиксируются в момент решения; ручной выбор — отдельным `manual_decision` + `manual_decision_at`, автоматика его не перезаписывает.

**Пересмотр:** при смене правил/профиля автоматически пересматриваются `rejected` и `needs_clarification` со старой версией; `skipped` — только явным `/unskip`. Повторное чтение по `last_read` (старше 7 дней) для не-терминальных. **«Отсев известных» при поиске только предотвращает дубль строки** — незавершённая обработка известных продолжается независимо (известность ≠ обработано).

### 16.3 Состояние и решения кластера (R4)

| Событие | Решение |
| --- | --- |
| новая публикация совпала с кластером `status='skipped'` | строка сразу `skipped` («пропущен кластер»), уведомление не создаётся |
| новая публикация совпала с активным кластером | строка в кластер; карточка (БД/outbox) пополняется ссылками и полями; **новое уведомление не создаётся** (уникальность карточки по кластеру) |
| слились два кластера с уже доставленными карточками | слияние молча; отправленные карточки не отзываются; дальше кластер живёт как один |
| представитель сменился (появилась запись hh) | `rep_job_id` обновляется; карточка пополняется ссылкой hh; повторное уведомление — только если карточка ещё не доставлена |
| разделение кластера (ложное слияние) | редкий случай: CLI-инструмент вне Telegram, пересоздание кластеров |
| правила оценивают кластер | проходит, если проходит **хотя бы одна** публикация; причина указывает источник |
| конфликты полей (зарплата/гео/описание) | хранятся по источникам, показываются в карточке по источникам; запись представителя не затирает остальные |

**Кандидаты дедупа:** точный ключ ∪ прямые ссылки в тексте ∪ эмбеддинг-top-K (K=5, окно 30 дней) — раздел 8. **Вход эмбеддинга:** название + компания + `requirements` (описание — только при пустых требованиях, с вычисткой шаблонов). **Версии:** вектор версионирован моделью и `content_hash` (R7).

### 16.5 Восстановление раунда (R5, утверждён 05.11.2026)

- **Граница `since` — `t_start` раунда, а не время завершения.** Перед опросом фиксируется `t_start=now()` (UTC); следующий раунд читает всё с прошлого `t_start`. Публикации, появившиеся во время обхода (гонка 12:00→12:02), попадают в следующий обход с перекрытием; дедуп по известным ID не создаёт дубль-уведомлений.
- **Атомарный коммит источника:** строки `jobs` + `search_report:<source>` + `last_search:<source>=t_start` — одной транзакцией. Обрыв → ничего не закоммичено → повторный обход того же окна (идемпотентно). Позиция пагинации **не персистится**; цена восстановления hh ≈ 16–40 с повторного обхода.
- **Команда `/search` не теряется:** приём команды = строка `round_requests(id, state)` сохраняется **до** квитирования обновления (продвижения `telegram_offset`); краш до сохранения → Telegram перешлёт обновление в течение 24 ч (свойство продукта). На старте `queued`/`active` → раунд доигрывается идемпотентно.
- **Состояния раунда:** `queued → active → waiting → done`. Новый `/search` в `queued`/`active` игнорируется; в `waiting` (часть источников на таймерах `RateLimited`) — **принимается**: запускается новый раунд для всех готовых источников, источники на таймере присоединяются к нему по срабатыванию (N8).
- **Честность покрытия:** первый обход канала, RSS-пагинация с ограниченной историей, длительный простой — помечаются `incomplete`/`coverage_gap` в отчёте; полнота истории не утверждается молча.
