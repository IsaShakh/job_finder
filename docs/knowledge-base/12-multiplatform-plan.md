# 12. Мультиплатформенный агент: отревьюенный план (v2)

> **Статус документа.** Целевой план переделки проекта в мультиплатформенный агент поиска вакансий. Зафиксирован 3 ноября 2026 года после двух независимых рецензий и решений пользователя. Файлы 01–11 описывают **текущее** состояние (`job-finder`, один источник hh.ru); этот файл — **целевое** состояние, по которому будет вестись работа.
>
> Исходники: [черновой план](../../plans/2026-11-02-multiplatform-job-agent-plan.md), [рецензия №1 (по коду)](../../plans/2026-11-02-multiplatform-plan-review.md), [рецензия №2 (внешняя) и слияние](../../plans/2026-11-02-plan-review-merge.md).

## 1. Цель и рамки

Один локальный асинхронный Python-процесс: собирает вакансии с выбранных площадок, убирает дубли между ними, фильтрует по согласованным правилам, готовит карточку (и, по решению по V1-объёму, письмо + советы по резюме) и присылает в Telegram. **Пользователь откликается сам.**

**Исключено:** автоотклик целиком (браузерная отправка, `HH_LIVE`, `resume_id`, `attempts` как активная таблица, статусы `sending`/`sent`/`unknown`, капча при отправке, `send_interval`); обход капчи и скрытые методы; деплой на сервер; выдумывание фактов.

**Явное исключение из «скрытых методов»:** программный API hh.ru в стиле официального Android-приложения (решение 30.10.2026, [ресёрч](../../research/2026-10-30-programmatic-api.md)). Способ доступа не является публично документированным API — риск отзыва ключей/блокировки принимается осознанно, браузерный фолбэк удаляется вместе с Playwright (решение зафиксировать в плане этапа 1).

**Свойство продукта (не баг):** пока компьютер спит/выключен, сбор не идёт и бот не отвечает; обновления Telegram хранятся ≤24 ч. Для круглосуточной работы нужен сервер — вне объёма.

## 3. Архитектура

Пакет `job_finder/`: `__main__.py` (CLI: init, configure, pair, doctor, run), `config.py`, `models.py`, `store.py`, `rules.py`, `dedupe.py`, `scoring.py`, `writer.py`, `llm.py`, `engine.py`, `telegram.py`, `adapters/` (`__init__.py` — реестр, `base.py`, `hh.py`, далее платформы).

Конвейер:

```
 адаптеры (параллельно, каждый по своему расписанию)
   search → SearchReport (hits + incomplete + notes)   [отчёт покрытия сохраняется]
        │
   отсев известных по базе + обновление last_seen      [водяной знак поиска на платформу]
        │
   fetch → каноническая Vacancy
        │
   дедупликация: точный ключ → кандидаты → эмбеддинги   [консервативно, см. раздел 8]
        │
   жёсткие правила (детерминированно, без LLM)
        │
   LLM-скоринг (информационный: оценка + причина)       [не блокирует]
        │
   writer: письмо + советы (сбой НЕ блокирует карточку)
        │
   outbox → Telegram (сводка топ-N + уточнения)
```

**SQLite + asyncio (принятое решение):** адаптеры параллельны, но в SQLite пишет **один потребитель** через `asyncio.Queue` (ядерный цикл остаётся детерминированным, синхронный sqlite3 не блокирует event loop в фоне). Повтор `RateLimited` — по персистентному таймеру на платформу (`settings: next_retry:<platform>`), чтобы рестарт не бомбил площадку.

**Планировщик:** у каждой платформы свои `last_search:<platform>` и интервал (`SEARCH_INTERVAL_<PLATFORM>` в `.env`); сбой одной изолирован (`AttentionRequired` паузует только её), обрыв поиска на середине не записывается как полный (водяной знак позиции).

## 4. Каноническая модель (исправления из рецензий)

Обе ошибки черновика устранены: PEP 604-синтаксис заменён на `Optional[...]` (стек: **Python 3.10+** — 3.9 EOL с 31.10.2025), поле без значения по умолчанию больше не стоит после полей со значениями. Добавлены явные поля для критериев (значение «неизвестно» сохраняется как `None`):

```python
from typing import Optional
from dataclasses import dataclass, field

@dataclass(frozen=True)
class Vacancy:
    source: str                    # "hh", "remoteok", ...
    native_id: str
    url: str                       # строит адаптер; ядро URL не собирает
    title: str
    company: str                   # очищенное название
    description: str
    requirements: str
    salary: Optional[Salary] = None          # minimum, maximum, currency, period, raw
    remote: Optional[bool] = None            # None = не подтверждено
    remote_geo: Optional[str] = None         # география удалёнки («только РФ», «из ЕС»…)
    location: Optional[str] = None           # город/страна офиса (для релокации: «Москва», «Дубай»…)
    timezone: Optional[str] = None
    employment: Optional[str] = None         # занятость
    salary_gross: Optional[bool] = None      # налоговый режим зарплаты
    published_at: Optional[str] = None
    closed: bool = False
    language: str = "ru"
    raw: dict = field(default_factory=dict)  # отладочный снимок платформы
```

## 5. Схема БД (целевая)

- `jobs` — ключ `id = source:native_id`; **каждая публикация источника — отдельная строка**; добавляются `source`, `published_at`, `cluster_id`, `last_seen`, `last_read`, `norm_company`, `norm_title` (индексированы — для кандидатов дедупа); удаляются `resume_id`, `evidence`, `attempts`.
- `clusters(id, rep_job_id, centroid BLOB, embedding_model TEXT, embedding_dim INT, created)` — группа дублей; представитель — hh при наличии.
- `job_embeddings(job_id PK, embedding BLOB, model TEXT, dim INT)` — векторы **версионированы**; смена провайдера/модели → пересчёт всех векторов.
- `llm_calls(id, job_id, kind, model, prompt_tokens, completion_tokens, cost, created)` — журнал стоимости.
- `application_history(...)` — **архив** истории откликов текущей версии (бывшие `attempts` + `sent`/`unknown`); не участвует в новых статусах.
- `settings`, `inbox`, `outbox`, `skip_events` — не «без изменений»: в `outbox` добавляются `job_id`/`cluster_id` и новый `kind` карточек; `settings` получает по-платформенные ключи.
- Статусы: `found` (известна, не прочитана), `read`, `rejected` (правила/скоринг-порог/`/skip`, с причиной), `needs_clarification`, `ready` (карточка готова, ждёт доставки), `delivered`, `closed`, `error`.
- **`/skip` действует на весь кластер** (все строки `cluster_id` → `rejected`, причина «пропущена пользователем»), иначе вакансия вернётся с другой площадки.

## 6. Протокол адаптера

```python
class SourceAdapter(Protocol):
    name: str
    def __init__(self, config): ...
    async def search(self, criteria, since) -> SearchReport   # hits + incomplete + notes
    async def fetch(self, key) -> Vacancy
    async def close(self): ...                                # время жизни HTTP-клиента
```

`search` возвращает дешёвые поля листинга **и признак полноты покрытия** (как текущий `search_report.incomplete` — не терять при рефакторинге); `since` — по `published_at`/водяному знаку платформы. Пагинация, аутентификация, лимиты, парсинг — внутри адаптера. Исключения: `AttentionRequired` (нужен человек), `RateLimited` (повторить позже), `VacancyUnavailable` (закрыта/удалена). Общие хелперы `adapters/base.py` **извлекаются из текущего `job_finder/hh.py`** (rate limiter 0.4 с, обновление токена, санитизация ошибок, пагинация — уже написаны и покрыты 22 тестами), а не пишутся заново.

Токены платформ: `.state/tokens/<platform>.json` (0600).

## 7. Правила отбора (v3, 03.11.2026)

**Регион источника** задаётся адаптером (`RU`/`intl`): hh, Habr Career, русскоязычные каналы → `RU`; RemoteOK, We Work Remotely, дубайские/зарубежные каналы → `intl`. Правила общие, различаются только региональным блоком. Реализация: `evaluate(vacancy, region)`.

Общие для всех регионов:

- **Python обязателен** в названии/описании/требованиях (как сейчас); нет → `rejected`.
- **Валюта не конвертируется**: зарплата в карточку отдаётся в исходной валюте (AED/USD/EUR/RUB…); RUB-порог применяется только к зарплатам в RUB.
- **Явный Junior/Trainee/стажёр** без подходящей зарплаты → `rejected` (правило уровня сохраняется).
- **Командировки** (для `RU`): упоминание → `rejected`, «без командировок» не считается.
- **Скоринг информационный**: оценка 0–100 и причина идут в карточку и ранжируют сводку; `skip` — только выше явного порога в конфиге (по умолчанию выключен). Оценка — не вероятность трудоустройства.
- Правило пропуска тестов: после удаления автоотклика решить — `rejected` или информационная метка в карточке (рекомендация: метка).

### 7.1 Россия (регион RU)

- **Формат**: удалёнка ИЛИ релокация/офис в **Москве** (уточнение 03.11.2026).
  - `remote=True` → подходит;
  - локация содержит Москву (офис/гибрид/релокация в Москву) → подходит, в карточке метка «офис/гибрид, Москва»;
  - `remote=None` и Москвы нет → `needs_clarification`;
  - `remote=False` и Москвы нет → `rejected`.
- **Поиск по hh идёт двумя ветками** с дедупом между ними: удалёнка (`schedule=remote`) + Москва (`area=1`, с учётом релокации). У Habr/каналов фильтрация по локации не применяется — решает правило выше.
- **Зарплата в RUB**: порог **150 000 ₽/мес**; вилка подходит, если верхняя граница ≥ порога (полная таблица трактовок — в дизайне 19.10, сохраняется); максимум ниже порога → `rejected`.
- **Если зарплата не указана ИЛИ валюта ≠ RUB** — берём в очередь при выполнении любого из:
  1. явный **грейд Middle+** (Middle/Mid/Senior/Lead/Principal/Staff/ведущий/тимлид/техлид); или
  2. **грейд не указан** (напр. «Python-разработчик», «Backend-разработчик») **+ Python-стек** в вакансии (FastAPI, Django, Flask, asyncio, SQLAlchemy, pytest и т.п.; слово «Python» в названии тоже считается) → берём.
  - Иначе → `rejected` («грейд и Python-стек не подтверждены»).
- Явная зарплата ниже порога в RUB → `rejected` независимо от грейда/стека.

### 7.2 Дубай и зарубежные вакансии (регион intl)

- **Формат**: удалёнка ИЛИ релокация/офис в целевом регионе (Дубай) — `remote=True`, либо локация/`remote_geo` содержит Дубай или признак релокации; иначе → `rejected`/`needs_clarification`.
- **Зарплата**: порог не применяется (любая), валюта отдаётся как есть, без пересчёта.
- **Грейд**: от Middle и выше; грейд не указан → как в RU: проверяем Python-стек, есть → берём; нет → `rejected`.
- Категории: обязательные (Python, формат, регион) / предпочтения (стек, отрасль, размер компании — влияют на порядок выдачи и объяснение) / неизвестные (зарплата, гео, грейд — обрабатываются правилами выше, ничего не теряется молча).

## 8. Дедупликация (консервативная)

Принцип: **для личного поиска лучше редкий повтор, чем потерянная вакансия.**

- Нормализация названия/компании: регистр, пунктуация, «Senior»/«Сеньор», юрформы.
- Точный ключ `(norm_company, norm_title)` — **только выбор кандидатов**, не слияние (одна компания может искать двух Python-разработчиков в разные команды).
- Сравнение — эмбеддинги по «название + компания + первые ~800 символов описания»; порог косинуса ~0.93 — **гипотеза**, подбирается на размеченных примерах.
- SimHash-fallback — **со своим порогом** (Hamming ≠ cosine); кросс-языковые дубли (hh ru vs RemoteOK en) fallback не ловит — фиксируется в отчёте.
- Сомнительное совпадение **не объединяется автоматически** (показывается отдельно с пометкой «возможно, дубль»).
- Конфликты полей кластера **не затираются**: зарплата/география/описание каждого источника сохраняются; политика слияния — таблицей в ADR.
- Повторное чтение: `last_seen`/`last_read`, детект изменения описания (хэш), переоценка не-терминальных записей при смене профиля/критериев, повторы после временных ошибок по таймеру.

## 9. LLM: скоринг, письмо, советы

- **Один или два прохода — решить** (см. раздел 14, рекомендация: один проход дешёвой моделью).
- **Верификация фактов обязательна** — свободная генерация не проверяется JSON-схемой. Варианты: (а) конструируемое письмо из утверждённых фраз с дословной сверкой, как сейчас в `letters.py` (нулевой регресс — рекомендация); (б) свободное письмо + проверочный проход; (в) свободное письмо + осознанный риск. Совет: каждый пункт совета имеет основание (какой пункт вакансии его вызвал + какой реальный опыт позволяет).
- «Минимум один совет» и «2–3 темы» — **не обязательны**: для идеального совпадения допускается 0.
- Кэш скоринга: ключ — хэш `(job_id, версия профиля, версия критериев, модель, версия промпта)`.
- Промпт-инъекция: вакансия — данные, не инструкции (и для скоринга, и для writer'а); вывод валидируется схемой; ретраи при невалидном JSON ограничены (2) и попадают в `llm_calls`.
- Сбой письма **не блокирует доставку карточки**.

## 10. Telegram

- **Сводка топ-N за цикл** (N в конфиге); карточка: должность, компания, зарплата, формат/ограничения удалёнки, причина соответствия, **все ссылки кластера**, оценка + причина; письмо/советы — в карточке или по `/letter` (по решению об объёме V1).
- `needs_clarification` — отдельным коротким сообщением; команды просмотра и ручного решения.
- Команды: `/status` (состояния платформ и очереди), `/history`, `/letter source:native_id`, `/skip source:native_id` (по кластеру), `/help`. `STATUS_LABELS` обновить (`read`/`delivered` вместо `sending`/`sent`/`unknown`).
- Outbox — единственный путь наружу: связь с `job_id`/`cluster_id`, защита от повторного создания одного уведомления, подтверждение отправки, учёт чанков (механика `telegram_chunk_<id>` уже есть). **Exactly-once не гарантируется**: редкий сбой после sendMessage может продублировать один чанк — допустимо, фиксируется в документации.
- `DELIVER` флаг в конфиге (false → карточки копятся в `ready`); глобальная пауза переопределяется как **пауза доставки**.

## 12. Миграция данных

- Бэкап через `Connection.backup()` (WAL-безопасный), затем `PRAGMA user_version` повышается; миграция идемпотентна, при первом запуске.
- Старые отклики (`sent`, `unknown`, `attempts`) → **архив `application_history`**, НЕ в `delivered/rejected` — это разные факты («отклик отправлен» ≠ «карточка доставлена»). «Без потери данных» подтверждается наличием архива.
- Пилотная запись `137924141` переносится в архив/историю hh; `id` → `hh:137924141` для существующих записей; письма и причины сохраняются, `Letter` при чтении получает дефолты новых полей.
- 31 запись `ready` со старыми письмами: доставить как есть или перегенерировать — решить в этапе 1b.
- `settings`: вычистить `HH_LIVE`, `next_send_at` и т.п.; добавить по-платформенные ключи и `DELIVER`.

## 13. Приёмка (4 результата)

1. **Пользователь считает выдачу полезной** — ручная оценка доставленных карточек и понятности причин отбора.
2. **Подходящие вакансии не теряются в отсеве** — проверка части отклонённых, неоднозначных случаев и ошибочных объединений.
3. **Перезапуск продолжает обработку** — прерывание на разных этапах: сохранённые данные, очередь, позиция поиска (водяной знак).
4. **Сбой одного источника/Telegram не останавливает остальное** — временная недоступность, 429, восстановление.

Дополнительно: стоимость LLM за цикл (с эмбеддингами), полнота охвата источников, поведение после длительного простоя.
