# 02. Архитектура

## Общая схема

Один асинхронный Python-процесс (asyncio) объединяет три параллельных контура, связанных через SQLite:

```
┌────────────────────────────────────────────────────────────────────┐
│  python -m hh_agent run  (один процесс, fcntl-блокировка)          │
│                                                                    │
│  ┌──────────────┐   ┌──────────────────┐   ┌───────────────────┐   │
│  │ Engine       │   │ Telegram.poll    │   │ Telegram.flush    │   │
│  │ (рабочий     │   │ (long polling,   │   │ (доставка из      │   │
│  │  цикл HH)    │   │  getUpdates)     │   │  outbox)          │   │
│  └──────┬───────┘   └────────┬─────────┘   └─────────┬─────────┘   │
│         │                    │                       │             │
│         ▼                    ▼                       ▼             │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │                 SQLite  .state/agent.sqlite3  (WAL)          │  │
│  │  jobs · attempts · settings · inbox · outbox · skip_events   │  │
│  └──────────────────────────────────────────────────────────────┘  │
│         │                                                        │
│         ▼                                                        │
│  ┌──────────────────┐      ┌─────────────────────────────────┐    │
│  │ Browser          │      │ LetterGenerator (httpx → LLM)   │    │
│  │ (Playwright,     │      │ OpenAI-совместимый Chat          │    │
│  │  persistent      │      │ Completions, JSON-режим)         │    │
│  │  context, hh.ru) │      └─────────────────────────────────┘    │
│  └──────────────────┘                                              │
└────────────────────────────────────────────────────────────────────┘
```

- Контуры **не блокируют друг друга**: сбой Telegram не останавливает поиск/отправку, работа с HH не ждёт доставки уведомлений.
- Всё состояние — в SQLite: при выключении компьютера прогресс сохраняется, при следующем запуске восстанавливается.

## Слои (модули `hh_agent/`)

| Модуль | Роль |
| --- | --- |
| `models.py` | «Словарь» типов: `Vacancy`, `Salary`, `Decision`, `Letter`, `Outcome`, исключения `AttentionRequired`, `VacancyUnavailable` |
| `config.py` | Загрузка и строгая валидация `.env` + переменных окружения; пути к состоянию; константа `RESUME_ID` |
| `rules.py` | Чистые функции правил отбора: `parse_salary`, `evaluate(Vacancy) → Decision` (без I/O) |
| `store.py` | Вся работа с SQLite: очередь вакансий, статусы, журнал попыток, настройки, inbox/outbox, восстановление |
| `hhapi.py` | **Основной источник вакансий**: программный API hh.ru (OAuth мобильного приложения) — поиск, чтение, отклик, подтверждение; интерфейс совместим с `Browser` |
| `browser.py` | Адаптер hh.ru через Playwright — теперь **запасной канал** (вход в браузер, редкие формы); только публичная навигация |
| `letters.py` | Генерация писем: неизменяемые факты профиля, строгая валидация ответа модели, детерминированный fallback |
| `telegram.py` | Telegram Bot API: owner-only опрос обновлений, команды-отчёты, доставка уведомлений частями с rate-limit |
| `engine.py` | Оркестратор рабочего цикла: поиск → подготовка → отправка → сверка → сводки; обработка пауз и блокировок |
| `__main__.py` | CLI, блокировка процесса, onboarding (`init/configure/pair/api-login/login`), запуск трёх контуров |
| `profile.json` | Единственный источник подтверждённых фактов профиля пользователя (двуязычные фразы + теги) |

## Рабочий цикл Engine

```
run()
└─ start()
   ├─ store.recover()            # sending→unknown; ready без письма→found
   ├─ сброс флагов поиска/сверки, browser_blocked, attention_reason
   ├─ если есть unknown → reconcile() → пауза, если остались unknown
   └─ search()                    # первый поиск при каждом запуске
└─ бесконечный tick() каждые ~2 с:
   1. browser_blocked? → стоп (ждёт ручного исправления и перезапуска)
   2. прошло SEARCH_INTERVAL (по умолч. 6 ч)? → search()
   3. live, не пауза, наступило next_send_at? → send(первая ready)
   4. иначе → prepare(первая found)
   5. раз в день → ежедневная сводка (digest)
```

**Поиск**: `GET api.hh.ru/vacancies` (text=Python, schedule=remote, order_by=publication_time, per_page=100, лимит 2000 результатов). ID дедуплицируются. Если выдача упирается в лимит — дополнительный обход по 4 диапазонам опыта (`noExperience`, `between1And3`, `between3And6`, `moreThan6`); отчёт честно помечает неполный охват.

**Подготовка** (`engine.prepare`): прочитать вакансию → обновить в БД → если уже откликался — пометить `sent` → применить `evaluate` → готово: сгенерировать письмо и сделать `ready`; иначе записать причину (`rejected` / `needs_clarification` / `closed`).

**Отправка** (`engine.send`): перед отправкой **заново** читается вакансия и перепроверяются правила; если условия изменились — письмо перегенерируется. Внутри источника (API или браузер):

1. свежая проверка «уже откликнулся» (для API — `relations` вакансии, для браузера — надпись на странице);
2. повторная оценка правил;
3. **gate** — последняя проверка «live && claim()» прямо перед отправкой (claim атомарно переводит `ready → sending` и пишет запись в `attempts`);
4. отправка: API — один `POST /negotiations`, подтверждение по списку откликов `GET /negotiations`; браузер — форма с одним кликом «Откликнуться» и ожиданием надписи «Вы откликнулись»;
5. `sent` только при подтверждении площадки; редирект на форму (анкеты/тесты) → `needs_clarification`; иначе `unknown` → пауза и ручная проверка.

**Сверка** (`engine.reconcile`): для строк `unknown` проверяется страница вакансии на надпись «Вы откликнулись»; отсутствие надписи **не** превращает статус в «не отправлено» — требуется ручная проверка истории HH.

## Модель параллельности и целостности

- **Один процесс**: `fcntl.flock` на `.state/agent.lock` не даёт запустить второй экземпляр.
- **Один отклик в полёте**: `claim()` атомарно (BEGIN IMMEDIATE) переводит строку в `sending`; второй отклик на ту же вакансию невозможен даже из другой сессии БД.
- **Намерение до клика**: всё, что произошло после `claim` и до подтверждения, при любом сбое завершается как `unknown` — повторная отправка автоматически запрещена.
- **Telegram и SQLite не делят транзакции**: доставка в Telegram и запись о доставке разделены; редкий сбой после отправки может продублировать **один чанк уведомления**, но не сам отклик.
- **WAL-режим** SQLite; файлы `-wal`/`-shm` нужно копировать вместе с базой при переносе.

## Запуск и команды CLI

```
.venv/bin/python -m hh_agent init       # создать .env (из .env.example) и .state/
.venv/bin/python -m hh_agent configure  # ключи: Telegram, LLM (скрытый ввод)
.venv/bin/python -m hh_agent pair       # одноразовая привязка владельца Telegram
.venv/bin/python -m hh_agent api-login  # вход в HH через API (пароль или код SMS/email)
.venv/bin/python -m hh_agent login      # запасной вход в HH в окне браузера
.venv/bin/python -m hh_agent doctor     # локальная проверка настроек
.venv/bin/python -m hh_agent search     # один поиск без отправки
.venv/bin/python -m hh_agent run        # основной режим (поиск+подготовка+отправка+Telegram)
.venv/bin/python -m hh_agent status     # пауза и счётчики очереди
```

Источник вакансий выбирается автоматически: есть `.state/api-token.json` → программный API; нет → браузерный путь.

Графические обёртки: [scripts/setup.command](../../scripts/setup.command) — меню настройки; [scripts/start.command](../../scripts/start.command) — сразу запускает агента.

## Внешние зависимости

- **Playwright** (Chromium в `.cache/ms-playwright`) — запасной браузерный канал (вход, редкие формы); постоянный профиль `.state/browser-profile`.
- **httpx** — Telegram Bot API, Chat Completions и API hh.ru.
- **python-dotenv** — чтение `.env`.
- **cryptography** — RSA-OAEP для `loginTrustFlags` при входе в HH через API.
- Требования закреплены в [requirements.lock](../../requirements.lock); проект — в [pyproject.toml](../../pyproject.toml) (Python ≥3.9, entry point `hh-agent`).
